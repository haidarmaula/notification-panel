# Previewing a subject erasure request

This operator query inventories dependencies for one exact **public application UUID, identity namespace and authenticated subject**. Use the identity owner’s verified mapping for the case. The account may have several subjects, installations and retired binding generations. The output covers the associated local user within that application. An external ID, email, device address or matching subject in another namespace cannot establish ownership.

## Running the preview

Obtain the deployment privacy and security owners’ case authorization, list of permitted tenants, legal-hold review and restricted evidence destination before accessing the inventory. Use a dedicated reader over verified TLS on the approved database. Its service profile should identify the intended database and authenticate the operator. Restrict network reachability and verify effective role membership and any tenant row filters. A query predicate scopes the report. Direct column grants permit other SELECTs on visible rows, so give the inventory role only to the authorized control plane or operators approved for its entire row scope. A tenant- or case-confined operator requires separately enforced row filtering or a restricted control-plane executor.

The optional [reader grants](../../scripts/sql/subject-erasure-reader-grants.sql) select only the columns used by the report. A database owner can apply them to a separately provisioned, reviewed reader with `psql -X -v ON_ERROR_STOP=1 -v preview_reader=APPROVED_READER -f scripts/sql/subject-erasure-reader-grants.sql service=notification_owner`. Keep the role free of schema creation, table writes, elevated memberships and inherited access to restricted columns. Pseudonymous identity lookup still needs restricted access. Configure database auditing to record the case/actor, query template, time, target and outcome without capturing bound identity values. Check statement logging, bind/error parameter logging, proxy logs and the evidence store before using a real subject.

Have the authorized case system supply one compact UTF-8 JSON object through protected standard input. It must contain exactly the following string fields. Encode control characters as JSON escapes inside the single record.

```json
{"application_id":"11111111-1111-4000-8000-000000000001","identity_namespace":"synthetic-application-issuer","subject":"synthetic-subject"}
```

From the repository root, run the [psql wrapper](../../scripts/sql/preview-subject-erasure.psql) using psql 17 or later.

```sh
psql -X -qAt -v ON_ERROR_STOP=1 -f scripts/sql/preview-subject-erasure.psql service=notification_privacy_reader < /protected/cases/selection.json
```

The wrapper binds the JSON through PostgreSQL’s extended protocol. The [query](../../scripts/sql/subject-erasure-impact.sql) returns one JSON object without echoing identifiers, addresses, proof verifiers, fingerprints, token material, Kafka bytes, provider IDs or profile fields. The transaction is read-only, uses a fixed search path and has a three-second statement limit and 250 ms lock limit. A timeout ends the attempt. Some owner lookups may scan existing indexes or tables before finding their matches. Measure IO on a representative protected replica before scheduling repeated previews. Review snapshot staleness against the authoritative writer before any later action. [psql parameter binding](https://www.postgresql.org/docs/17/app-psql.html).

Record the timestamp, case reference, authorized operator, database/restore identity and count report in the restricted case record. The case record maintains the link to the original selection. An unresolved selection returns `groups: null`. This includes an unknown project, namespace or subject and an ambiguous or malformed selection. Reconcile the identity mapping before proceeding.

## Interpreting the snapshot

- **Scope and routing.** Identity mappings include aliases for the selected user. Installations count current owners. Binding generations count current and retired ownership. The held-route count describes the last recorded destination for current generations. The stored application, runtime and hold flags are context for investigation. A release, authorization or legal decision requires its current policy and provenance.
- **Delivery.** Pending intents, ever-charged deliveries, still-unresolved charges and the latest unconfirmed dispositions may overlap. The latter two can persist after an owner, lease or terminal-status change. Provider acknowledgements count deliveries with local acceptance evidence. These counters cannot reconstruct the number of historical provider attempts or prove delivery, recall or provider erasure. User read rows and device observation rows have different units.
- **Related campaigns.** Campaign-level counts use the union of frozen intents, direct individual targets, scoped legacy deliveries and scoped read rows. The preview counts live and expired unreleased leases, preparation holds, unpublished campaign sends and attributed replay attempts. An unresolved physical quarantine position can lack a trusted campaign link. The preview avoids inspecting raw Kafka bytes. Unprepared broadcast/segment/upload audiences may still include the person even when every linked campaign count is zero. Update-outbox counts refer only to this subject’s frozen delivery generations.
- **Limits and external owners.** Every source stops at its 501st match. `coverage: exact` means the observed group is complete within its defined relational scope. When a source or required parent set reaches 501, dependent groups return `coverage: lower_bound`; individual counts may be zero in the inspected subset. A new query on large scopes need not choose the same subset. Obtain a separately reviewed keyset inventory to establish complete totals in that case. Unknown counts are JSON null, including downstream copies, published Kafka messages, source identity token issuance, unlinked legacy or quarantine history, raw uploads/payload mentions, provider custody, legal holds, archives and recoverable backups. A zero held-retention-class count cannot clear a legal hold.

## Erasure and sealed recovery

The inventory issues no deletion, tombstone, credential change or route decision. The following order is the implementation and evidence boundary for a future approved erasure workflow.

1. Independently verify the requester’s authority, the exact subject/user aliases and the applicable restrictions, holds and retention exceptions. Record a restricted case ID, the approved purposes and owners, and a non-reusable scope identifier. Inventory both modern and legacy writers, deployed clients, credential/consent source, provider and downstream stores. Resolve truncated and unknown groups through their owners.
2. Fence new enrollment, targeting and upstream issuance for the affected subject. Advance ownership generations and prevent legacy or delayed writers from reactivating old destinations. Verify transferred installations’ current owners before changing any binding. Preserve historical binding/user identity for pending work. Quiesce and explicitly dispose of pending sends, leases and charged uncertainty under the applicable dispatch protocol. Reconcile the provider, broker and external outcomes. A local timeout, rollback or route hold cannot recall an accepted push.
3. Before removing or anonymizing detail, obtain the retention/hold decision, freeze required history and preserve deduplication and replay evidence. Coordinate cache, search, analytics, backup and export custodians. Store the authoritative erasure/restriction record in the independently protected ledger under an approved lifetime at least as long as reintroduction is possible. Its custody and verification must survive loss of the application database.
4. A reviewed consumer contract must define the non-reusable scoped identifier, monotonically ordered restriction/erasure version, stable event ID, database/source lineage, idempotent application, durable per-consumer checkpoints, replay behavior and acknowledgement evidence. Historical imports and older events must be unable to recreate a restricted projection. Agree how each consumer handles gaps, duplicates, out-of-order records and restored lineages. Obtain consumer compatibility and reconciliation evidence before authorizing publication. The current send and delivery-update contracts have no erasure event.
5. Restore in isolation with ingress, dispatch, maintenance, consumer replay and provider egress fenced. Verify the independently approved database identity, restore horizon, keys and source lineage. Reapply all relevant post-backup erasures, revoked bindings, credentials, holds and access restrictions from the external ledger before readers, writers or consumers resume. Reconcile consumer versions/checkpoints and downstream acknowledgements. Re-run the scoped inventory and check that a previously restricted person cannot regain eligibility, recover a destination or be reconstructed by old messages. Keep the environment sealed if the ledger, key custody or acknowledgements are incomplete. [Sealed restore procedure](sealed-restore.md).

Production approval still requires the legal basis, owner-assigned lifetimes, an independent ledger, approved recipient dispositions, archive/backup policy and verified consumer contracts. [ADR-10](../adr/adr-10-retention-recovery.md).
