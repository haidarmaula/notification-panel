# Development tool requirements by task

Start with the [machine setup guide](../setup.md) for fresh-machine installation
and the [developer guide](../development-guide.md) for the usual first checks.
This page lists tools by capability so backend contributors can keep their
install small. Version references reflect the repository's current module,
package, generated-code, or CI configuration; recheck those sources when updating
tooling.

## Plain Go unit tests and builds

Required: the Go toolchain in [`go.mod`](../../go.mod), currently Go 1.26.11.
Use the official [Go installation instructions](https://go.dev/doc/install).
`./dev` and the repository shell scripts use Bash; install Bash if your system
does not already provide it.
For ordinary Go tests and builds, Docker, `.env`, PostgreSQL, Kafka, Node,
Python, `migrate`, SQLC, Postman, Playwright, and provider credentials are not
needed. Go may download the toolchain or modules on a first run.

The CI race gate runs `go test -race`. The Go race detector requires cgo to be
enabled, and a C compiler on non-Darwin systems; see the
[Go race detector requirements](https://go.dev/doc/articles/race_detector#Requirements).
A race run is optional when doing only a focused non-race unit check.

The project vulnerability gate is `bash scripts/ci.sh vuln`. The script installs
`govulncheck` v1.9.0 into a temporary directory and removes it afterward; do not
install a global scanner for this check. The vulnerability database lookup
requires network access and can change over time.

## Complete local application stack

`./dev up` needs Bash, Go, Python 3, Node 22.12 or newer, pnpm 11.25.0, and a
running Docker Desktop/Engine with Compose 2.24.4 or newer. See the official
[Docker installation](https://docs.docker.com/get-docker/) and [Compose
installation](https://docs.docker.com/compose/install/), [Python downloads](https://www.python.org/downloads/),
[Node downloads](https://nodejs.org/en/download), and [pnpm installation](https://pnpm.io/installation).
The dashboard package declares pnpm 11.25.0 in its `packageManager` field; CI
uses Node 22.23.4 and pnpm 11.25.0. Those exact versions are the project's
tested dashboard toolchain. Upstream defaults may be newer.

`nvm` is optional. If it is already installed, the runner can select a
compatible installed Node 22 when the active Node is too old; the runner never
installs Node or changes global toolchains. See [full local development](../local-development.md)
for startup, login, persistence, checks, and shutdown.

The local runtime does not need host-installed PostgreSQL, Kafka, `migrate`,
SQLC, Postman, Playwright, or repository `.env`. It runs private local services
in Docker, owns its synthetic development settings, and does not load staging
credentials. Keep those local credentials and Docker volumes together as the
local guide explains.

## Dashboard and browser checks

Dashboard formatting, lint, unit tests, build, and bundle budget checks need
Node 22.23.4 and pnpm 11.25.0. Install dependencies from the dashboard package
with `pnpm install --frozen-lockfile`. The package manager version is declared
in [`web/dashboard/package.json`](../../web/dashboard/package.json); Node is
pinned in the [dashboard CI workflow](../../.github/workflows/ci.yml).

The end-to-end browser suite also needs the Go toolchain for its real Go BFF,
Playwright's Chromium browser, and the browser's system dependencies. From
`web/dashboard`, install those with:

```bash
pnpm exec playwright install --with-deps chromium
```

This command may install operating-system packages on Linux and can require
administrator privileges there. The dashboard [README](../../web/dashboard/README.md)
describes fixture coverage and local browser runs. The persistent `./dev` stack
already installs package dependencies on startup; run the Playwright browser
installer only when executing a browser check.

## Database and SQL authoring

This toolchain is only for schema/query authoring. It is not required by plain Go
tests, builds, or `./dev`.

- `make` is required to use repository Make targets. Every target reads
  `.env` because the Makefile includes it at startup. Start from
  [`.env.example`](../../.env.example) for local authoring values; do not point
  migration commands at a shared or deployed database without the environment
  owner's instructions. The private settings generated by `./dev` are separate.
- SQLC v1.31.1 is recorded in the generated SQLC header. Install that version
  using Go's [official SQLC installation method](https://docs.sqlc.dev/en/latest/overview/install.html):

  ```bash
  go install github.com/sqlc-dev/sqlc/cmd/sqlc@v1.31.1
  ```

- `migrate` is needed for migration file creation and for applying migrations
  with Make. CI pins golang-migrate v4.19.1; install its CLI with the PostgreSQL
  build tag using Go:

  ```bash
  go install -tags postgres github.com/golang-migrate/migrate/v4/cmd/migrate@v4.19.1
  ```

Both Go-installed commands land in `GOBIN` when it is set, or in
`$(go env GOPATH)/bin` by default. Add that directory to `PATH` in the shell where you
will use them, then verify the executables and versions:

```bash
if [ -n "$(go env GOBIN)" ]; then
  export PATH="$(go env GOBIN):$PATH"
else
  export PATH="$(go env GOPATH)/bin:$PATH"
fi
command -v sqlc migrate
sqlc version
migrate -version
```

A Go-installed migrate binary can print `dev` because its release-version
string is set separately at build time. Confirm the pinned module version with
`go version -m "$(command -v migrate)"`; its module path should show v4.19.1.

Create a paired six-digit migration with `make migrate-create NAME=...`, then
edit the SQL and regenerate code with `make sqlc`. The new migration must exist
before SQLC generation. Never hand-edit `internal/database/sqlc/`. `make
migrate-up` uses the host URL built from `.env` and does not connect to the
unpublished database inside `./dev`; inspect `DB_URL` and confirm the target
database with its owner before applying changes. See the
[agent reference](../agent-reference.md#generated-code-and-migrations) for the
repository invariants.

## Opt-in integration checks

The `bash scripts/integration.sh` runner is separate from both unit checks and
`./dev`. It needs Bash, Docker with Compose, Go, Python 3, `migrate` v4.19.1,
and Postman CLI v1.75.0. Install migrate with the command above. Postman's
[CLI installation guide](https://learning.postman.com/docs/postman-cli/postman-cli-installation/)
describes supported installation methods; for the project's pinned version,
download the matching official archive:

| Host | Postman CLI v1.75.0 archive |
| --- | --- |
| Linux x64 | [linux64](https://dl-cli.pstmn.io/download/version/1.75.0/linux64) |
| Linux arm64 | [linux_arm64](https://dl-cli.pstmn.io/download/version/1.75.0/linux_arm64) |
| macOS Intel | [osx_64](https://dl-cli.pstmn.io/download/version/1.75.0/osx_64) |
| macOS Apple silicon | [osx_arm64](https://dl-cli.pstmn.io/download/version/1.75.0/osx_arm64) |

Unpack the archive into a user-owned installation directory, retaining all its
contents. Add that directory to `PATH` and create a `postman` symlink to its
`postman-cli` binary, as CI does. Verify `command -v postman` resolves to that
installation and `postman --version` reports 1.75.0. CI verifies the SHA-256 for its Linux x64
archive in [the workflow](../../.github/workflows/ci.yml); do not reuse that
Linux checksum for another platform.
The runner uses isolated fixture services and fixed local ports, and does not
read development `.env` or staging credentials. Read the
[integration guide](../development-guide.md#5-exercise-infrastructure-in-isolation)
and its evidence links before running it.

## Other optional repository checks

- `go tool mockery` uses the tool dependency declared in `go.mod`; no global
  `mockery` installation is needed. Use it only when changing an interface with
  generated mocks.
- `python3 scripts/check-api-contracts.py` needs Python 3 and the validator
  packages named in the script's module docstring: `openapi-spec-validator`
  0.7.2 and `jsonschema[format-nongpl]` 4.23.0. Use a local virtual environment
  rather than global `pip` installation. CI's setup is a reference:

  ```bash
  python3 -m venv /tmp/hello-contracts
  /tmp/hello-contracts/bin/pip install 'openapi-spec-validator==0.7.2' 'jsonschema[format-nongpl]==4.23.0'
  /tmp/hello-contracts/bin/python scripts/check-api-contracts.py
  ```

  This check does not need the Go, dashboard, Docker, or provider toolchains.
- `python3 scripts/check-onboarding.py` needs Python 3 and Bash. Its `--run`
  option additionally invokes the safe Go examples and may download Go
  dependencies.

## Operational drill prerequisites

These are optional, isolated engineering drills. Use the named runbook for the
exact command, fixture ownership, and evidence limits before running one.

| Drill | Host tools and fixture requirements | Details |
| --- | --- | --- |
| Kafka replication | Bash, Docker with Compose, Go, Python 3, OpenSSL, and the pinned Kafka image already present locally. `--monitor` also needs the pinned monitoring images and curl to fetch the JMX exporter, unless `HELLO_KAFKA_JMX_JAR` points to a verified local copy. | [Kafka replication drill](../runbooks/kafka-replication-drill.md) |
| PostgreSQL PITR | Python 3, Docker with a local Unix socket, and the pinned PostgreSQL 17 image already present locally. OpenSSL and PostgreSQL backup tools run inside the disposable image. | [Physical PITR drill](../runbooks/physical-pitr.md) |
| Monitoring validation | Bash, Python 3, Docker, and network access or locally available digest-pinned Prometheus and Grafana images. | [Monitoring runbook](../runbooks/monitoring.md#local-validation) |
| Sealed restore and worker rollback | The sealed-restore prerequisites: Docker, Go, Python 3, migrate, Postman CLI, and Compose, plus full Git history containing the script's fixed prior revision. `GOFLAGS=-race` additionally needs the race detector prerequisites above. | [Sealed restore runbook](../runbooks/sealed-restore.md) |

Operational scripts create disposable local resources; inspect their target
and cleanup behavior before starting. This guide does not authorize changes to a
deployment, shared database, credentials, or protected files.
